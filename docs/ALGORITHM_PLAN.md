### 3.2 변경 시 주의점

1. Google 검색 응답에 이미 평가가 있다. 정렬용으로 식당마다 Details를 추가 호출하지 않는다.
2. Google·카카오 ID를 보존하고 이름이 같다고 자동 병합하지 않는다. 기존 북마크·후기 참조를 바꾸지 않는다.
3. Google 메모리 저장과 북마크 ID 저장 구조를 유지한다. 추천 점수를 장소 원본·localStorage·게시글에 복제하지 않는다.
4. 현재 페이지 최대 15곳 기준으로 정렬한다. 전체 최대 45곳 순위로 표현하지 않는다.
5. 페이지 토큰은 메모리, 페이지 번호는 검색 상태에 저장된다. 3페이지 새로고침은 앞 페이지부터 토큰을 다시 받아 최대 3회 검색할 수 있다.
6. 검색·상세는 서버 `auth.requireUser()`를 거친다. 로컬 데모 로그인만으로 Google API가 허용된다고 가정하지 않는다. 사진은 로그인 대신 15분 서명 URL 검증을 사용한다.
7. revision은 늦은 응답 반영을 막지만 현재 검색 클라이언트는 외부 AbortSignal을 받지 않는다. 화면 변경이 진행 중인 유료 요청까지 취소한다고 표현하지 않는다.
8. 서버는 개수 누락·비정상 값을 0으로 정규화한다. 추천에는 양의 정수만 사용한다. 누락과 실제 0개 구분은 별도 보완이다.
9. 정렬 대상은 전체 메모리 Map이 아니라 현재 `searchResult.restaurants` 또는 선택 북마크의 후보다. 과거 검색 식당을 섞지 않는다.
10. `renderList()`는 갤러리 정리 후 DOM을 다시 만든다. 정렬만 바꿀 때 사진·영상 재조회가 늘지 않도록 갱신 범위를 검토한다.

## 4. Google 연동과 화면에 관한 선결 조건

### 4.1 카카오 유지 요구와 공식 정책

Google 서비스별 약관 14.2는 Places API 콘텐츠를 비 Google 지도와 연계해 사용하는 것을 제한한다. 현재 코드는 Google 장소·평가·좌표를 카카오 지도와 연결하고 있다. 동작하는 구현이 있다는 사실과 공개 운영이 허용된다는 판단을 구분하며, 앞서 승인받은 조건부 설계를 유지한다. [서비스별 약관 14절](https://cloud.google.com/maps-platform/terms/maps-service-terms)

카카오 지도 유지 요구는 보존하며 다음 중 허용 가능한 구성을 확인한 뒤 공개 운영 방향을 확정한다. 이번 기획서 수정에서는 지도나 제공자를 임의로 교체하지 않는다.

| 대안 | 장점 | 제약과 확인 사항 |
| --- | --- | --- |
| A. 카카오 검색·지도 화면과 지도 없는 Google 평가 비교 흐름을 분리 | 기존 지도 유지 가능성, 평가 비교 목적 유지 | 단순히 지도만 숨기거나 탭을 나누는 것으로 충분하다고 단정하지 않음. 실제 연계 방식에 대한 허용 여부 확인 필요 |
| B. Google Places UI Kit로 평가 표시 | 약관 15.1에는 비 Google 지도와 사용 가능한 별도 예외 존재 | API 원시 별점을 추출해 자체 정렬하는 것까지 허용한다는 의미는 아님. 표시만 원하는 경우의 대안이며 본 정렬 기능과 동일하지 않음 |
| C. 평가 비교 화면에 Google 지도 사용 | Places API 표시 방식에 맞춘 구성 가능 | 카카오 지도 유지 요구와 다르므로 사용자 동의 필요 |
| D. 허용되는 다른 평가 데이터로 알고리즘 구현 | 카카오 화면과 독립적인 정렬·추천 구현 가능 | Google 평균 별점 기능과 다름. 자체 게시판 후기 평균·개수를 쓸 경우 별도 출처로 표시 |

이 문서의 Google 연동은 조건부 설계다. 데이터 수집 없이 합성 데이터로 Java 알고리즘 구현·검증을 준비하는 일은 독립적으로 진행할 수 있다. 약관 해결 전에 ‘Google 별점과 카카오 지도가 연동되는 서비스 구현 완료’로 제출하지 않는다.

### 4.2 필요한 Google 데이터와 비용

핵심 값은 `rating`과 `userRatingCount`다. 후자는 본문이 없는 평가도 포함하는 전체 평가 개수이므로 ‘가져온 후기 글 개수’로 표현하지 않는다. 평균 별점·개수와 자체 서비스 회원의 후기 점수는 합치지 않는다. [Place 리소스](https://developers.google.com/maps/documentation/places/web-service/reference/rest/v1/places)

현재 Text Search (New)로 식당을 직접 검색하고 Place Details (New)로 저장 ID의 최신 장소·사진을 재조회한다. 식당 간 매칭 단계는 필요 없다. 별점·평가 개수는 Enterprise 과금 필드이므로 실제 요금·한도는 사용하는 계정 기준으로 확인한다. 정렬 전환은 이미 받은 값을 사용해 추가 API 호출 없이 수행한다. [Text Search 공식 문서](https://developers.google.com/maps/documentation/places/web-service/text-search), [필드별 과금 구분](https://developers.google.com/maps/documentation/places/web-service/data-fields)

`GOOGLE_PLACES_API_KEY`는 이미 서버 전용 설정이고 `/api/config`에는 구성 여부만 제공된다. 검색어 길이·사진 서명·로그인 검사는 구현되어 있다. 계정별 요청량 제한 등 추가 비용 보호는 별도 검토한다. 예산 알림이나 현재 로그인 검사만으로 과금 상한이 보장된다고 표현하지 않는다.

### 4.3 저장 및 출처

Google place ID는 저장 가능한 예외다. 현재 Google 장소 객체는 메모리에, 북마크는 ID로 저장하고 게시글에는 ID와 고정 안내값을 넣는다. 이 분리 구조를 유지하며 별점·평가 개수·Google 이름/주소·추천 점수 스냅샷을 영구 카탈로그·게시글·분석 로그에 복제하지 않는다. 기존 이미지 API의 10분/24시간 캐시를 Places에 그대로 적용하지 않는다.

화면에는 Google Maps 공식 출처 표시와 반환된 추가 출처를 반영하고 공개 이용약관·개인정보처리방침을 준비한다. 사용자가 새로고침하거나 북마크를 다시 열면 평가 정보를 재조회하고 실패 시 저장된 과거 점수를 최신값처럼 제시하지 않는다. [Places 정책 및 출처 표시](https://developers.google.com/maps/documentation/places/web-service/policies)

## 5. 알고리즘 적용 기획서 #1

### 내용

안정 병합 정렬을 이용한 별점·평가 개수 기반 맛집 정렬 서비스.

### 적용 알고리즘

복합 비교자를 사용하는 안정 병합 정렬(Merge Sort).

### 알고리즘 개요

목록을 절반씩 나눈 뒤 각 부분을 정렬하고 병합한다. 두 값이 같으면 왼쪽 값을 먼저 선택해 입력 순서를 보존한다. 입력이 이미 정렬되었거나 역순이어도 최악 시간 복잡도는 O(n log n)이다. 보조 배열 O(n), 재귀 스택 O(log n)을 사용한다. 작은 실제 목록에서는 내장 정렬도 충분하지만, 과제 제출에서는 분할·병합 과정을 직접 구현해 동작과 복잡도를 설명한다.

### 적용 서비스

맛집 검색 결과의 ‘별점순’과 ‘평가 많은 순’ 선택 기능. 기본값은 별점순이다.

### 적용 서비스 개발 개요

현재 페이지의 Google 검색 응답을 입력으로 사용한다. 정규화된 별점과 평가 개수를 다시 검증하고 최초 응답 인덱스를 연결한 뷰를 만든다. 유효한 평가 후보를 먼저 배치하고, 별점 내림차순·평가 개수 내림차순·최초 Google 순서로 비교한다. 평가 많은 순은 개수와 별점의 우선순위를 바꾼다. 서버가 개수 누락을 0으로 정규화하므로 0개는 평가 정보 없음 그룹에 넣는다. 북마크에서는 Google·기존 카카오 후보를 보존하며 평가 없는 장소를 아래에 표시한다.

정렬은 순수 함수로 만들고 원본 배열·장소 객체를 변경하지 않는다. 화면은 원래 검색 순서와 정렬된 목록을 분리하고 검색순으로 돌아갈 수 있게 한다. 정렬 선택값만 기존 검색 상태에 추가하고 점수 스냅샷은 저장하지 않는다. 선택 식당·북마크 ID·페이지 토큰을 보존하며 승인된 지도 구성에서는 마커 번호도 목록과 맞춘다. 정렬 전환으로 검색·Details를 반복하지 않고 갤러리 재조회도 최소화한다. Java에 같은 비교자·병합 정렬을 구현해 공통 입력의 결과 ID 순서를 비교한다.

### 정렬 규칙과 예시

| 우선순위 | 별점순 | 평가 많은 순 |
| --- | --- | --- |
| 1 | 평가 정보 유효 여부 | 평가 정보 유효 여부 |
| 2 | 평균 별점 내림차순 | 평가 개수 내림차순 |
| 3 | 평가 개수 내림차순 | 평균 별점 내림차순 |
| 4 | 최초 입력 순서 | 최초 입력 순서 |

유효한 평가는 유한한 별점 1~5와 양의 정수 평가 개수를 갖춘 Google 장소다. 0개·누락·잘못된 값·기존 카카오 장소는 추천 점수 계산에서 제외하되 목록에는 보존한다. 검색은 최초 Google 순서, 북마크는 저장된 ID 배열 순서로 동점을 처리한다. Details worker 완료 순서를 동점 기준으로 쓰지 않는다. API 장애와 평가 없음은 구분한다.

합성 예시: A(4.8점, 30개), B(4.8점, 300개), C(4.9점, 2개), D(평가 없음)이면 별점순은 C → B → A → D다. 별점과 개수를 모두 곱하는 규칙으로 기본 정렬을 바꾸지 않는다.

## 6. 알고리즘 적용 기획서 #2

### 내용

베이지안 가중 평균을 이용한 평가 표본 보정 맛집 추천 서비스.

### 적용 알고리즘

평균 별점과 평가 개수에 사전 기준을 결합하는 가중 평균 점수 계산. 계산한 점수의 정렬에는 #1의 병합 정렬을 재사용한다.

### 알고리즘 개요

평가가 적은 식당은 기준 평균의 영향을 크게 받고, 평가가 충분한 식당은 자신의 평균 별점에 가까운 점수를 얻는다. 평균·표본 수만 이용하는 휴리스틱으로, 신뢰구간이나 실제 맛의 확률을 계산하는 통계 모델이라고 주장하지 않는다.

```text
S = (v × R + m × C) / (v + m)
R: Google 평균 별점
v: Google 전체 평가 개수
C: 사전 기준 평균, 초기 제안 4.0
m: 사전 가중치, 초기 제안 50
```

C와 m은 데이터로 검증된 최적값이 아닌 조정 가능한 초기 설정이다. 현재 페이지 평균으로 C를 계산하면 페이지 이동·후보 추가 때 점수가 바뀌므로 1차 구현에서는 고정값을 사용하고 화면 도움말에 공개한다. 점수 계산 O(n), 정렬 포함 O(n log n), 결과 배열·병합 버퍼를 포함한 공간 O(n)이다.

### 적용 서비스

사용자가 선택하는 ‘보정 추천순’. 기본 별점순과 별도 옵션으로 제공한다.

### 적용 서비스 개발 개요

Google 평균 별점만 정렬하면 평가 1개의 5.0점 식당이 평가 500개의 4.7점 식당보다 먼저 나타난다. 이 기능은 현재 응답의 평가 개수를 사용해 적은 표본의 극단적인 점수를 완화한다. 추가 API 호출이나 리뷰 수집은 필요 없다. 유효한 평가 후보에만 S를 계산하고, 추천순은 S·원본 별점·평가 개수·최초 입력 순서로 비교한다. 순위 계산은 반올림하지 않고 화면에만 소수 둘째 자리까지 표시한다. Java와 웹은 동일한 경계·동점 규칙을 사용한다.

카드에는 ‘Google 평균 별점 4.7 · 평가 500개’와 ‘서비스 보정 점수 4.64’를 구분해 보여준다. 보정 점수를 Google이 제공한 별점으로 표현하지 않는다. 추천 이유는 ‘평균 별점과 평가 개수를 함께 반영’처럼 실제 입력값으로 설명한다. 평가가 많다는 이유만으로 음식의 질이나 리뷰 진실성을 보장하지 않는다. 평가 정보가 없는 식당은 원래 검색 순서를 유지해 목록 아래에 표시하며 실패 안내를 제공한다. 검증에는 작은 표본·큰 표본·동점·누락·경계값을 포함하고, m 변경이 순위에 주는 영향을 합성 데이터로 비교한다.

### 계산 예시

아래는 실제 식당 데이터가 아닌 검증용 값이다. C=4.0, m=50을 사용한다.

| 식당 | 평균 별점 | 평가 개수 | 보정 점수 | 결과 |
| --- | --- | --- | --- | --- |
| A | 5.0 | 1 | 4.0196 | 소수 평가의 극단값을 보정 |
| B | 4.7 | 500 | 4.6364 | 충분한 표본의 높은 평점 반영 |
| C | 4.5 | 100 | 4.3333 | 중간 표본 반영 |

별점순 A → B → C, 보정 추천순 B → C → A. 이것이 사용자가 두 옵션을 비교할 수 있는 대표 시연이다.

## 7. 추가할 만한 알고리즘

| 우선순위 | 기능 | 자료구조·알고리즘 | 복잡도와 의미 |
| --- | --- | --- | --- |
| 카카오 검색 복귀 시만 | 카카오·Google 동일 식당 판별 | 이름 토큰 유사도 + Haversine + 주소/지점 규칙 | 현재 Google 직접 검색에는 불필요. 검색 제공자 변경 때만 별도 검토 |
| 선택 추가 | 상위 5곳 추천 | 최소 힙 Top-K | O(n log k), 공간 O(k). 전체 정렬 O(n log n)과 결과·성능 비교 가능. 실제 15~45곳에서는 실용적 이득이 작음 |
| 후속 | 출발점에서 가까운 순 | Haversine 거리 계산 + 병합 정렬 | O(n log n). 직선거리이며 이동시간·도로거리와 다름 |
| 후속 | 저장한 맛집의 방문 순서 | 최근접 이웃 탐욕법 | O(p²), 방문 상태 O(p). 출발점을 고정한 근사 동선, 최적 보장 없음 |
| 심화 | 소규모 최적 방문 순서 | 비트마스크 DP(Held-Karp) | O(p²·2^p), 공간 O(p·2^p). 선택 10곳 이하 제안, 같은 거리 기준으로 탐욕법과 비교 |

Top-K는 추천 요약만 필요할 때 사용한다. 전체 정렬한 뒤 앞의 5개를 자르는 결과와 같아야 하며, 이미 전체 목록 정렬이 필요한 화면에 힙을 추가해 성능이 개선됐다고 주장하지 않는다. 그래프가 없는 직선거리 완전 그래프에 Dijkstra를 적용해 방문 순서 최적화라고 부르지 않는다.

## 8. 기존 Google API를 재사용하는 적용 설계

### 8.1 데이터와 상태

```text
GoogleRestaurant: 현재 응답 객체, google ID·별점·평가 개수·사진·출처
KakaoRestaurant: 기존 저장 객체, kakao ID·기본 장소 정보
RankingInput: 현재 페이지 또는 선택 북마크 순서에 맞춘 후보 배열
RankedView: restaurant 참조·originalIndex·유효 평가 여부·보정 점수
SortState: 검색순 / 별점순 / 평가 많은 순 / 보정 추천순
```

RankedView는 일시적인 결과이며 저장 함수·북마크·게시글 입력에 포함하지 않는다. SortState만 기존 검색 상태에 추가할 수 있다. 이전 저장 데이터에 선택값이 없으면 기본 별점순을 적용하고 알 수 없는 값은 허용 목록으로 정규화한다.

새 검색은 `searchResult.restaurants`를 입력으로 사용한다. 누적 메모리 Map의 다른 검색 식당은 섞지 않는다. 북마크 입력은 저장된 restaurantIds 순서로 구성한다. 재조회 실패와 평가 없음은 구분하고 실패한 장소를 0점 식당처럼 추천하지 않는다.

### 8.2 페이지와 API 호출

현재 페이지 최대 15곳을 정렬하며 다음 페이지는 새 후보 안에서 다시 정렬한다. 화면에 현재 페이지 기준임을 밝힌다. 정렬 옵션은 페이지 이동에도 유지하지만 전체 최대 45곳의 통합 순위로 표현하지 않는다.

Google 응답 한 번에 후보별 평가가 포함되므로 15곳 첫 조회는 일반적으로 Text Search 한 번이다. 이전 기획의 식당별 Google 매칭 요청은 삭제한다. 사진은 별도 media 요청이며 북마크 복원은 저장 Google ID마다 Details 호출이다. 페이지 새로고침의 앞 페이지 토큰 재확보도 별도 호출이다. 정렬·추천 전환 자체에는 추가 Places 호출을 만들지 않는다.

전체 최대 45곳 정렬은 향후 3페이지를 수집·ID 중복 제거한 후 한 번 정렬하는 별도 기능이다. 그때는 최초 인덱스·부분 실패·취소·호출량을 정의해야 한다. 현재 페이지 토큰 기능만 두고 전체 순위를 표기하지 않는다.

### 8.3 재사용할 구현과 보완

| 이미 구현됨 | 알고리즘 작업 |
| --- | --- |
| Google 검색·상세·사진 중계 | 기존 API 재사용, 식당별 평가 보강 API 불필요 |
| 별점·평가 수 표시 | 정렬 선택·보정 점수·추천 이유·범위 안내 추가 |
| 메모리 장소 저장·ID 북마크 | 점수도 일시적으로 유지, 원본 불변 검사 |
| Google·카카오 게시글 연결 | 양쪽 ID 유지, Google 평가와 자체 후기 점수 분리 |
| 검색 revision 방어 | 정렬 변경과 늦은 응답 충돌 검사. 네트워크 취소는 별도 보완 후보 |
| 사진 갤러리·확대·출처 | 디자인 유지, 순서만 바꿀 때 불필요한 재조회 줄이기 |
| 로그인 검사·사진 서명 | 유지. 요청량 제한은 현재 구현과 별도 비용 보호 검토 |

## 9. Java 제출과 웹 적용 구조

### 9.1 확정 방향: 독립 실행 제출 모듈

현재 Node.js 배포를 유지하고 `algorithm-java/`에 Java 8 호환 소스·합성 입력·실행 안내를 추가한다. 제안 구성은 `RestaurantCandidate`, `StableMergeSort`, `BayesianRanker`, `AlgorithmDemo`, `AlgorithmTest`, `Benchmark`다. Java에서는 배열/List와 Comparator를 사용하고 병합 정렬을 직접 구현한다.

동일한 합성 fixture로 기본 정렬·보정 추천의 ID 순서와 점수 오차를 검증한다. Google·카카오 출처 혼합·결측·복원 완료 순서 변경도 포함한다. 별점은 double, 평가 개수는 long, 최초 순서는 int로 다루되 웹의 안전한 정수 범위와 같은 입력 범위를 적용한다. 함수는 외부 API·DB 없이 실행하며 출력 로케일 차이는 비교에서 제외한다.

사용자는 독립 실행 Java 코드와 웹의 동일 입력·결과 검증 방식을 확정했다. 웹과 Java에 동일 알고리즘이 각각 존재하는 구조이며 웹 요청이 Java를 실제 실행한다고 표현하지 않는다. 수업별 제출 세부 기준은 별도 확인 사항으로 남긴다.

### 9.2 참고: 향후 Java 웹 실행으로 범위가 변경되는 경우

이 절은 현재 구현 범위에 포함하지 않는다.

평가 조회를 담당하는 Node.js가 정규화한 입력을 Java 정렬/추천 실행기로 보내고 결과를 받아 화면에 전달하는 구성을 추가한다. 서버 실행 시 한 번 기동하는 Java 프로세스 또는 별도 Java API 서버를 후보로 비교한다. 사용자 요청마다 컴파일하거나 명령 문자열에 사용자 입력을 결합하지 않는다.

현재 Render Node 런타임에 JRE가 있다고 가정할 수 없으므로 Java 포함 컨테이너 또는 별도 Java 서비스·실행 환경을 구성해야 한다. 프로세스 실패·입출력 제한·시간 초과·배포 검증까지 포함해 일정이 늘어난다. Spring 전체 전환은 이 알고리즘 과제의 기본안으로 잡지 않는다.

## 10. 검증과 성능 평가

| 구분 | 검증 항목 | 완료 기준 |
| --- | --- | --- |
| 기본 정렬 | 별점 동점·개수 동점·완전 동점·빈 배열·역순·결측 | 비교 규칙과 안정성 충족, 원본 불변 |
| 보정 추천 | 5.0/1과 4.7/500, m 경계, 유효하지 않은 입력 | 예시 순위 일치, NaN/Infinity 없음, 유효 점수 1~5 |
| Java·웹 비교 | 동일 fixture ID 순서와 점수 | 순서 완전 일치, 점수 절대 오차 1e-9 이하 제안 |
| 출처·입력 순서 | Google·카카오 혼합, Details 완료 순서 변경 | 평가 없는 후보 보존, 북마크 ID 순서로 안정 동점 처리 |
| API | 키 누락·403·429·시간 초과·손상 응답·취소 | 비밀정보 비노출, 요청 상한 준수, 실패 상태 분리 |
| 저장 | 새로고침·북마크·공유 게시글 | 정렬 선택값만 저장, Google 평가/점수 스냅샷 복제 없음, 양쪽 ID 유지 |
| 화면 | 정렬 변경·선택 유지·늦은 응답·390px 화면 | 화면 넘침 없음, 최신 검색 결과만 표시, 기준 설명 접근 가능 |
| 호출량 | 정렬 옵션 반복 변경 | 검색·Details·사진 요청이 불필요하게 증가하지 않음 |
| 기존 기능 | 회원·게시판·관광·영상·이미지·북마크 | 기존 54개 검사 및 변경 관련 검사 통과 |

`tests/google-places.test.js`의 공급자 순서 유지 검사는 서버 API 계약으로 보존한다. 화면 정렬을 추가한다고 서버 검사도 별점순으로 바꾸지 않는다. 새 알고리즘은 API 응답 이후 별도 계층에서 검사한다. 카카오·Google 매장 매칭 정확도 측정은 현재 직접 검색 범위에서 제외한다.

성능 입력은 실제 Google 데이터를 대량 수집하지 않고 합성 후보 15·45·1,000·10,000·100,000개를 사용한다. 랜덤·이미 정렬·역순·동점 다수를 포함한다. 작은 크기의 단순 정렬과 직접 병합 정렬을 비교하고, 큰 입력에서 느린 O(n²) 기준 구현의 실행 범위를 제한한다. 선택 시 Top-K는 전체 정렬 상위 k개와 결과가 같아야 한다.

웹은 고해상도 타이머, Java는 `System.nanoTime()`을 사용한다. 준비·워밍업 후 반복 측정하고 중앙값, 실행 환경, 입력 seed, 반복 횟수를 기록한다. 입력 생성·복사·알고리즘·외부 API 대기 시간을 분리한다. Java 메모리는 보조 배열 크기의 이론값과 관측 힙 사용량을 구분하고 GC 영향도 적는다. 15개에서 빠르다는 이유로 대규모 성능 개선을 입증했다고 표현하지 않는다.

## 11. 작업 순서와 예상 범위

Google 매칭·중계 신규 개발이 불필요해 남은 기본 작업은 약 4~6시간으로 수정한다. 공개 운영 정책 해결·실제 API 계정 준비·대규모 화면 변경은 제외한 추정이다. Java는 독립 제출이므로 웹 연동·배포 전환은 포함하지 않는다. 실제 연결 검증이 미완료라면 알고리즘 검증과 구분해 기록한다.

## 12. 구현 전 확인할 사항

1. **Google 평가와 카카오 지도:** 사용자가 원하는 조합은 보존하되 약관상 허용 가능한 구성을 확인해야 한다. 단순 탭 분리나 출처 로고만으로 해결됐다고 가정하지 않는다.
2. **Java 제출 범위 확정:** 독립 실행 소스 + 웹 동일 입력·결과 검증으로 진행한다. Java 웹 서버와 배포 런타임 변경은 포함하지 않는다.
3. **결제·요청 예산:** Places API (New) 활성화와 테스트 호출 허용량을 확인한다. 비밀키는 문서·채팅에 기록하지 않고 서버 환경변수로 관리한다.
4. **평가 본문:** 별점·전체 평가 개수만으로 시작한다는 제안이다. 개별 리뷰 본문이 필요하면 표시 의무·과금·별도 필드 조회를 추가 기획한다.
5. **과제 판정:** 병합 정렬 + 보정 점수 계산을 2개로 인정하는지, Java 버전·제출 저장소·MySQL 사용이 별도 필수인지 확인한다.

현재 구현값은 페이지당 최대 15곳·화면 최대 3페이지, Google·카카오 ID 병행, Google 복원 worker 2개다. 추가 제안은 기본 별점순·선택 보정 추천순·검색순 복귀·C=4.0/m=50이다. 정렬 전환에는 외부 조회 큐를 새로 만들지 않는다. 신규 설정은 아직 적용된 값이 아니다.
