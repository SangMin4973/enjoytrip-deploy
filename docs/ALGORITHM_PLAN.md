# 맛집기행 알고리즘 적용 기획서

수정일: 2026-10-15<br>
현재 상태: 최대 45곳 수집·Java 정렬 및 보정 추천 구현 완료. 서버 Java 실행과 웹 정렬 선택 연결 완료.

## 적용 목표

현재 Google Places API로 조회하는 음식점의 평균 별점(`rating`)과 평가 개수(`userRatingCount`)를 활용해 **별점순 정렬**과 **보정 추천순 정렬**을 추가한다. 기존 검색 결과를 입력으로 사용하므로 알고리즘 적용을 위한 외부 API 추가 호출은 필요하지 않다.

적용 범위는 검색 한 번에 수집한 최대 3페이지·45곳이다. 전체 후보를 정렬한 뒤 15곳씩 표시하는 방향을 유지한다. 지역 내 모든 음식점의 순위를 뜻하지 않는다. 현재 웹은 기본 별점순이며 검색순·평가 많은 순·보정 추천순도 선택할 수 있다. 검색순은 Google 응답 순서를 사용한다. 다음·이전 페이지 이동은 수집한 배열을 분할하므로 재검색하지 않는다.

## 알고리즘 적용 기획서 #1

### 내용

안정 병합 정렬을 이용한 별점·평가 개수 기반 맛집 정렬 서비스.

### 적용 알고리즘

병합 정렬(Merge Sort)과 복합 비교자.

### 알고리즘 개요

음식점 목록을 절반씩 나누어 정렬한 뒤 두 목록을 병합한다. 별점이 높은 음식점을 우선하고, 별점이 같으면 평가 개수가 많은 음식점을 먼저 배치한다. 두 조건이 모두 같으면 기존 검색 순서를 유지한다.

- 자료구조: 음식점 배열과 병합용 보조 배열
- 시간 복잡도: O(n log n)
- 공간 복잡도: O(n)

### 적용 서비스

맛집 검색 결과의 기본 정렬인 **별점순**.

### 적용 서비스 개발 개요

Google 검색 응답에서 수집한 전체 후보와 전체 최초 수집 순서를 정렬 입력으로 사용한다. 직접 구현한 Java 병합 정렬의 비교 기준은 ① 별점 내림차순, ② 평가 개수 내림차순, ③ 최초 검색 순서다. 평가 많은 순은 개수와 별점의 우선순위를 바꾼다. Google 출처이고 유한한 별점 1~5점·양의 평가 개수를 가진 후보만 평가가 유효하다. 평가 정보가 없는 후보와 기존 카카오 후보는 삭제하지 않고 목록 아래에 최초 순서대로 유지한다.

정렬 함수는 화면 처리와 분리하고 원본 배열을 변경하지 않는다. Java 구현은 CLI와 웹 서버에서 공용으로 실행한다. 전체 후보를 정렬한 결과를 페이지로 나누고, 선택된 음식점과 북마크는 장소 ID를 기준으로 유지한다. 정렬 범위가 이번 검색에서 수집한 최대 45곳이라는 안내를 표시한다.

### 적용 예시

| 음식점 | 평균 별점 | 평가 개수 | 정렬 순위 |
| --- | --- | --- | --- |
| A | 4.8 | 30 | 3 |
| B | 4.8 | 300 | 2 |
| C | 4.9 | 2 | 1 |

## 알고리즘 적용 기획서 #2

### 내용

베이지안 가중 평균을 이용한 평가 개수 기반 맛집 추천 서비스.

### 적용 알고리즘

베이지안 가중 평균 방식의 보정 점수 계산. 계산한 점수는 #1의 병합 정렬로 정렬한다.

### 알고리즘 개요

평가가 적은 음식점의 높은 별점이 과도하게 순위에 반영되는 문제를 완화한다. 평가 개수가 적으면 기준 평균의 영향을 크게 받고, 평가 개수가 많으면 해당 음식점의 평균 별점에 가까운 점수를 얻는다.

```text
보정 점수 = (v × R + m × C) / (v + m)

R: 음식점 평균 별점
v: 음식점 평가 개수
C: 기준 평균 4.0
m: 보정 가중치 50
```

C와 m은 초기 설정값이며 검증 결과에 따라 조정할 수 있다. Java CLI에서 변경할 수 있고, C는 유한한 1~5점, m은 유한한 0 이상의 값만 허용한다. 보정 점수는 비교를 위한 서비스 자체 지표로, 실제 음식의 맛이나 평가의 진실성을 보장하지 않는다.

- 자료구조: 음식점별 보정 점수 배열
- 점수 계산 시간 복잡도: O(n)
- 정렬 포함 시간 복잡도: O(n log n)
- 정렬 포함 공간 복잡도: O(n)

### 적용 서비스

맛집 검색 결과에서 선택할 수 있는 **보정 추천순**.

### 적용 서비스 개발 개요

전체 수집 후보 중 Google 출처이고 별점이 유한한 1~5점이며 평가 개수가 양의 정수인 음식점에 보정 점수를 계산한다. 보정 점수 내림차순으로 정렬하고, 점수가 같으면 원본 별점·평가 개수·최초 검색 순서로 비교한다. 평가 정보가 없거나 유효하지 않은 음식점은 점수를 계산하지 않고 목록 아래에 표시한다.

Java의 점수 계산·추천 정렬은 구현했으며, 웹 목록의 정렬 선택 기능으로 별점순과 보정 추천순을 전환하도록 한다. 평균 별점·평가 개수와 보정 점수를 구분해 표시하고, 추천 기준을 간단히 설명한다. 계산에는 반올림 전 점수를 사용하고 화면에는 소수 둘째 자리까지 표시한다. 점수는 현재 화면에서만 사용하며 북마크나 게시글에 저장하지 않는다.

### 적용 예시

아래 값은 알고리즘 확인을 위한 가상 데이터다. C=4.0, m=50을 적용한다.

| 음식점 | 평균 별점 | 평가 개수 | 보정 점수 | 추천 순위 |
| --- | --- | --- | --- | --- |
| A | 5.0 | 1 | 4.02 | 3 |
| B | 4.7 | 500 | 4.64 | 1 |
| C | 4.5 | 100 | 4.33 | 2 |

별점순에서는 A가 먼저 나오지만, 보정 추천순에서는 평가 개수가 충분한 B가 먼저 나온다.

## 구현 및 완료 기준

| 구현 항목 | 현재 상태 및 완료 기준 |
| --- | --- |
| Java 제출 | `algorithm-java/`의 Java 8 호환 독립 실행 모듈에 기본 정렬·보정 추천 구현 완료 |
| 데이터 호출 | 기존 Google 수집기를 재사용해 최대 45곳을 Java 입력으로 전달. 식당별 평가 조회 추가 없음 |
| 정확성 검증 | 기본 정렬 65개 단언, 세 모드 fixture ID 순서, 추천 점수 오차 1e-9 이하·동점·결측·잘못된 값·원본 보존 검사 통과 |
| 성능 검증 | 합성 데이터 15·45·1,000·10,000·100,000개의 기본 정렬 측정 완료. 추천·웹 성능은 미측정 |
| 기존 기능 확인 | Node 검사 68개 통과. 검색·페이지 이동·상세·북마크 동작 유지 |
| 웹 화면 연결 | 전체 후보 정렬 후 페이지 분할, 선택 음식점·상세 유지, 점수와 기준 안내 구현 |
| Java·웹 결과 비교 | 실제 Java 프로세스·HTTP API·브라우저 어댑터로 동일 예시 ID 순서·점수 오차 1e-9 이하 검사 통과 |

Java 구현은 `StableMergeSort`의 복합 비교자와 제네릭 안정 병합 정렬을 `BayesianRanker`가 재사용한다. 보정 점수는 별도 `RankedRestaurant`에 보관하고 원본 장소와 평가 값은 변경하지 않는다. 실행 방법과 검사는 [Java README](../algorithm-java/README.md), 실제 기본 정렬 성능 결과는 [성능 기록](ALGORITHM_BENCHMARK.md)을 따른다.

Node.js 서버가 미리 컴파일한 Java `WebRankingMain`을 표준 입출력으로 실행한다. `js/restaurant-ranking.js`는 요청·원본 ID 연결만 담당하며 정렬 알고리즘은 Java에만 둔다. Render는 postinstall에서 Temurin JDK 17을 내려받아 체크섬을 검증하고 빌드한다. 요청마다 컴파일하지 않으며 동시 2개·5초·JVM 힙 32MB로 제한한다. 실패 시 기존 결과와 순서를 보존하고 재시도할 수 있다.

Google 장소 객체와 보정 점수는 메모리에서만 사용하고 북마크·게시글에는 Google 평가나 점수 스냅샷을 복제하지 않는다. API 키는 서버 환경변수로 관리한다. 정렬 전환을 위한 검색·Details 추가 호출은 만들지 않는다.

이번에 병합한 웹 변경은 검색 결과 화면에서 지역·메뉴를 수정해 다시 검색하는 기능이다. 정렬 구현과는 별개이며 기존 수집·페이지 분할 구조를 유지한다.

거리순 정렬과 방문 동선 생성은 후속 범위다. 기존 지도 연계의 공개 운영 검토는 알고리즘 구현 범위와 별도로 유지한다. 과제에서 병합 정렬과 보정 점수 계산을 두 알고리즘으로 인정하는지와 제출 세부 기준은 수업 기준으로 확인한다.
